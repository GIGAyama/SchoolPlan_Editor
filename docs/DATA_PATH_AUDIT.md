# 週案データの読み書き経路 監査

## 目的

このアプリの保存先はGoogleスプレッドシートだけで、画面に出ている内容がそのまま書き込まれます。
そのため「画面のデータが別のものに入れ替わる」「書き込みが別の場所へ向く」といった不具合は、
そのまま利用者のデータ喪失になります。

この文書は、週案データの読み込み・保存にかかわる全経路を洗い直した記録です。
見つかった問題と、それぞれをどう塞いだか、まだ残っている前提を書いてあります。

## 全体像

読み書きは次の経路に分かれます。監査ではこの全部を対象にしました。

| 経路 | 入口 | 書き込む範囲 |
|---|---|---|
| 週案の読み込み | `getWeeklyPlanDataV2` | 読み取りのみ（対象週7日分） |
| 手動保存 | `saveWeeklyPlanDataProtected('manual-save')` | 対象週の入力列 |
| 画面切替時の自動保存 | `saveWeeklyPlanDataProtected('auto-save')` | 同上 |
| 閲覧モードのセル操作 | `saveWeeklyPlanDataProtected('view-mutation')` | 同上 |
| 固定時間割の週転記 | `applyTimetableToWeek` | 時程・朝学習・1〜6校時 |
| 固定時間割の年間一括転記 | `processBulkTransferWithExclusion` | 同上（長期休業を除く） |
| 行事予定PDFの反映 | `applyExtractedEventsFromWeb` / `processEventPdf` | 行事・放課後 |
| 一括自動入力 | `batchAutoFillFromWeek` | 単元・学習内容 |
| 単元のずらし | `runShiftLessons` | 同上 |
| 振り返りの保存 | `saveDailyReflection` | 振り返り・振り返り状態 |
| 復元ポイントからの復元 | `restoreWeekSnapshotFromWeb` | 対象週の入力列 |
| データベースのクリア | `clearDatabaseDataProtectedFromWeb` | 入力列すべて |

## 見つかった問題と対処

### 1. 保存の応答が、応答待ちのあいだの操作を巻き戻していた

閲覧モードのセル操作は450ms待ってから自動保存しますが、GASの往復には数秒かかります。
サーバは「シートに実際に入った値」を返し、クライアントはそれで手元のデータを揃えていました。
その結果、応答を待つあいだに行った操作がまとめて巻き戻り、その状態がそのまま保存されていました。

右クリックメニューの「この日の全コマをクリア」を曜日ごとに続けて使うと、
月・火・水と消したあたりで火・水が復活する、という形で表面化していました。

**対処**

- 手元のデータを書き換えるたびに通し番号を進め、保存要求を出した時点から変わっていない時だけ
  サーバの応答を取り込む（`weekDaysMutationSeq` / `adoptSavedWeekDays`）
- 保存に送る内容は要求時点のスナップショットにし、送信後の書き換えを巻き込まない
- 進行中の保存の後に待たせる保存は週ごとに1件へまとめる。待っている1件は実行時に
  最新の内容を読み直すため、待機中に増えた変更も取りこぼさない
- 週を移動したあと・編集モードに入ったあとに返ってきた応答では、画面と手元のデータを書き換えない

### 2. 「元に戻す」が別の週・別の学級の内容を持ち込んでいた

セル操作の履歴（元に戻す／やり直す）は週データの配列そのものを積んでいますが、
週を移動しても学級を切り替えても捨てていませんでした。

- 別の週で「元に戻す」→ 表示中の週が前の週の内容に置き換わる
- 同じ週の別の学級で「元に戻す」→ 日付が一致するため、**別の学級の内容がそのまま保存される**

**対処**

履歴に「どの学級のどの週のものか」を持たせ、表示中の範囲と食い違ったら捨てます
（`STATE.historyScope` / `ensureHistoryScope`）。履歴を積む・使う・メニューの有効無効を決める、
すべての入口から通すため、読み込み側で捨て忘れても食い止められます。

### 3. 編集中の入力が、あとから届いた読み込み結果で消えていた

週の読み込みは「キャッシュを即描画 → 数秒後にサーバ応答で描き直す」という二段階です。
その間に編集を始めていると、応答が届いた時点で入力が丸ごと消えていました。

**対処**

未保存の入力があるあいだは、読み込み結果で画面を描き直さないようにしました（`p2ApplyWeekData`）。
ただし固定時間割の転記・復元・DBクリアのように、サーバ側を書き換えた直後の読み直しは
手元の内容より優先します（`{ force: true }`）。

### 4. 学級を切り替えた直後の保存が、別の学級のシートへ向いていた

保存先はサーバ側の「アクティブな学級」で決まります。クライアントが学級を切り替えたあとに
前の学級の保存が届くと、別の学級の週案を上書きしていました。

**対処**

- 週移動・学級切替・画面切替の前に、待たせてある保存を先に送る（`flushPendingViewSave`）
- 保存要求に、書き込むつもりだった学級シート名を添える。サーバ側で照合し、
  食い違っていたら書き込まずに理由を返す

### 5. シート全体を読んで丸ごと書き戻していた

固定時間割の週転記・年間一括転記、行事予定PDFの反映、一括自動入力、単元のずらしが、
シート全体を読んで `setValues` で書き戻していました。これには2つの問題があります。

- 曜日・週番号・時程などの**数式列が、計算結果の静的な値に置き換わる**（以降まったく再計算されない）
- 読み込みから書き戻しまでのあいだに他から入った変更を、読んだ時点の値で巻き戻す

**対処**

変更した行の、必要な列だけを書くようにしました（`p2WriteChangedWeekRows_` / `p2WriteColumnValues_`）。
固定時間割の転記と一括自動入力は、週案の保存と同じ ScriptLock で直列化しました。

### 6. 固定時間割の転記が「月曜の行から5行連続」を前提にしていた

行の抜けや並び替えがあると、別の日付へ転記していました。日付で行を引き当てるようにし、
DBに行が無い日は結果として報告します。あわせて年間一括転記の長期休業除外を、
週単位から日単位に変えました（週の途中から始まる休業も正しく除外されます）。

### 7. 対象週に含まれない日付の保存要求が、成功扱いになっていた

送られた日付の行が対象週に無い場合、何も書かずに「保存しました」と返していました。
画面側の状態がずれていても気づけないため、対象週外の日付が混ざった要求は弾くようにしました。

### 8. 保存前スナップショットを、クライアントから無効化できた

`saveWeeklyPlanDataV2` は `google.script.run` から直接呼べるうえ、第4引数の `options` をそのまま
受け取っていたため、`{ protect: false }` を渡すだけで保存前スナップショットを飛ばせました。

実装本体をクライアントから呼べない `saveWeeklyPlanWeek_` へ移し、
公開する入口では保護を必ず有効にしました。

### 9. データベースのクリアが入力を消し残していた

「時程〜放課後」の連続範囲を消していたため、放課後より右にある宿題・持ち物が残っていました。
また列順の違うシートでは、消してはいけない列を巻き込む形になっていました。
論理列を指定して消すようにしました。

### 10. 年間走査がシート全体を読んでいた

時数集計（週を移動するたびに走る）と振り返り状況（起動のたびに走る）が、
学習内容などの長い列を含めてシート全体を読んでいました。集計に使う列だけを読むようにしています。

読み込みは少数の連続範囲へまとめます。列ごとに読むと転送量は減っても往復が増えて逆に遅くなるためです。
代表的な列構成では31列中18〜19列・2〜3回の読み込みになります。

### 11. 閲覧モードのセル操作が、読み込み応答に上書きされていた

編集モードを経ずに閲覧モードのままコマを動かす・消すと、保存できないことがありました。

閲覧モードの変更は、編集モードと違って入力欄ではなく `STATE.weekData.days` にしか入りません。
週を開くときはキャッシュを先に描いてから数秒後にサーバ応答を当てるため、
「週を開いてすぐ操作する」だけで応答が操作の上に重なります。
そこで `STATE.weekData` ごと差し替えていたため、

- 動かしたコマが画面から消え、操作が無かったことになる
- 手元のリビジョンが保存前へ巻き戻り、以降の保存が毎回「保存の競合」で弾かれる

という壊れ方をしていました。編集モードは `hasUnsavedChanges()` で守られていた経路です。

あわせて、保存後のキャッシュ更新（`p2UpdateCurrentWeekCache`）が
「画面に出ているデータの週」を `STATE.mondayStr`（＝これから表示したい週）で上書きしていました。
週を移動した直後は「移動先を読み込み中・画面は移動元」という時間があるため、
そこで保存が通ると移動元の内容が移動先の週としてキャッシュされ、
以降その週の保存が「その週に含まれない日付」として弾かれていました。

**対処**

- どの週に未確定の閲覧モードの変更があるかを週ごとに控え（`markViewWeekDirty` /
  `markViewWeekSaved`）、`p2ApplyWeekData` は表示中の週が未確定のあいだ差し替えを見送る。
  キャッシュも書き換えない（保存前の内容を残さないため）
- 保存が通った時点で未確定を解除する。手元の内容を捨てると決めた読み直し
  （競合時の「最新を読み込む」・サーバ側を書き換えた直後の強制読み直し）では
  `p2DiscardLocalEdits` がまとめて捨てる
- `p2UpdateCurrentWeekCache` は週の識別にデータ自身の `mondayDateStr` を使う
- 閲覧モードの週移動は、送った保存の応答を待ってから読み込む（`loadWeeklyPlan`）。
  保存が飛んでいるのはセル操作の直後だけなので、通常の週移動は待たされない

## まだ残っている前提

正直に書いておきます。

| 前提 | 内容 |
|---|---|
| **読み込みはロックを取らない** | `getWeeklyPlanDataV2` は ScriptLock を取りません。保存の書き込みが複数の範囲に分かれるため、ごく短い時間だけ途中状態を読む可能性があります。読み込みにロックを掛けると、バックアップやスナップショット作成の裏で週移動が数秒止まるため、その待ち時間のほうが実害が大きいと判断しました。読み違えた場合も、次の読み込みか保存時の競合検出で必ず気づけます |
| **クライアントの週キャッシュは5分** | 別端末での変更が最大5分は画面に出ません。ただし読み込み直後にサーバの値で必ず描き直すため、表示が古いままにはなりません |
| **本番での確認はしていない** | この作業環境から `script.google.com` へは到達できません。`.gs` の変更はテストデプロイで確かめてからマージしてください |
| **振り返りの保存はシート全体を読む** | `saveDailyReflection` は週まとめの自動生成で年間分を参照します。1日1回の操作のため未着手です |

## 確かめかた

```bash
npm run quality
```

読み書きの回帰テストは次の2つです。どちらも静的な検査ではなく、実物のコードを動かします。

- `tests/week-data-integrity.test.mjs` … 実物のクライアントコードをサンドボックスへ読み込み、
  DOMとサーバ呼び出しと `setTimeout` だけを差し替えて動かします。応答が遅れる状況、
  週や学級をまたぐ操作、編集中の入力の保護を再現します
- `tests/db-write-path.test.mjs` … 実物の `.gs` を偽のスプレッドシート上で動かします。
  数式列を書き込み範囲に含めないこと、日付で行を引き当てること、
  学級や対象週の食い違いを弾くことを確かめます
- `tests/view-mutation-save.test.mjs` … 閲覧モードの自動保存のレースを再現します

いずれも、修正前のコードでは失敗することを確認したうえで入れてあります。
